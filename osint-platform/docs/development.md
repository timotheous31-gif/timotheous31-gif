# Development

## Setup

```bash
make install                  # backend venv (Python 3.12) + frontend deps
createdb osint
make migrate
make seed                     # optional demonstration case, fixture data only
make dev                      # API :8000, dashboard :3000
```

Redis is optional in development: the cache falls back to an in-process map and
jobs run inline when no broker is reachable. `CELERY_TASK_ALWAYS_EAGER=true`
forces inline execution explicitly.

## Everyday commands

```bash
make test          # backend pytest + frontend vitest and typecheck
make lint          # ruff, black --check, mypy
make lint-fix      # ruff --fix and black
make cov           # coverage, HTML report in backend/htmlcov
make migration m="add x"   # autogenerate a migration
make worker        # a Celery worker
make docker-up     # the whole stack
```

## Layout

```
backend/app/
  api/          routers; thin, delegate to services
  cli/          Typer commands; same service layer as the API
  collectors/   one module per source, plus base/registry/runner
  correlation/  extraction, confidence, resolver
  core/         settings, logging, db, http, ssrf, ratelimit, cache, errors
  graph/        backend ABC + NetworkX implementation
  models/       SQLAlchemy models
  privacy/      classifier, filter, secret detection
  reporting/    model + renderers + templates
  schemas/      Pydantic request/response models
  services/     business logic: normalisation, cases, engine, jobs, evidence
  workers/      Celery app and tasks
frontend/
  app/          Next.js App Router routes
  components/   UI primitives and case-scoped components
  hooks/        data-fetching hooks
  lib/          typed API client and formatters
  types/        API types mirroring the backend schemas
```

## Conventions

**Errors are recorded, never swallowed.** `except Exception: pass` does not
appear in this codebase. Where a failure must not stop the pipeline, it is
caught, typed, logged and attached to the run or the result.

**Comments explain why, not what.** If a line needs a comment to say what it
does, it usually needs rewriting instead.

**Types everywhere.** `mypy` runs over `app/`; the frontend uses TypeScript
strict mode with `noUncheckedIndexedAccess`.

**Tests are hermetic.** An autouse fixture answers name resolution from a fixed
table and raises on anything else, so a test that would reach the real network
fails loudly. Outbound HTTP is mocked with `respx`. Sample data uses reserved
documentation domains and invented handles only.

**Migrations are verified against PostgreSQL**, not just autogenerated:
upgrade, downgrade and `alembic check` all run before a schema change lands.

## Writing a test

Unit tests exercise pure functions against fixtures:

```python
def test_mx_records_expose_mail_hosts(collector):
    finding = collector.normalize(payload("MX", ["10 mail.example.com."]), target)[0]
    assert finding.data["mail_hosts"] == ["mail.example.com"]
```

Integration tests drive the API through `httpx.ASGITransport` with an in-memory
database, using the `api_client` and `case_id` fixtures.

When a test needs collectors, replace the registry rather than the network:

```python
monkeypatch.setattr("app.services.engine.load_builtin_collectors", lambda: None)
_REGISTRY.clear()
_REGISTRY[StubCollector.name] = StubCollector
```

## Before you push

```bash
make lint && make test
```

Both must be clean. If you changed the schema, regenerate the migration and
verify it round-trips on PostgreSQL. If you added a promise to the README, add
the test that makes it falsifiable.
